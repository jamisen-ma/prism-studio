# Independent review: smooth Curves

Status: **implemented backend independently audited, 8/8 native and 3/3 pure-client maintained tests passing; client source clear and owner reports 8 focused plus 51 adjacent browser workflows passing**. The existing linear Curves path remains unchanged. This review owns `tests/smooth-curves-audit.test.mjs`, `tests/smooth-curves-client-audit.test.mjs` and `test-results/smooth-curves-review/`; the architect owns the proposal and prototype in `test-results/curves-evaluation/`.

## Recommendation

An optional `parameters.interpolation: 'smooth'` is a useful bounded extension to existing Curves. Omitted interpolation and explicit `'linear'` mean the existing linear operation; canonical records omit `'linear'`. Smooth uses the current 2–16 control points, channels and arbitrary finite ordered input coordinates, including adjacent and subnormal values. It must not tighten legacy point spacing or silently round saved coordinates.

The proposed mathematical rule is a shape-preserving cubic Hermite interpolant with weighted harmonic interior derivatives and limited one-sided endpoints. A zero secant or sign change gives a zero shared derivative. This permits locally increasing, decreasing, flat and reversing tone curves without forcing the complete curve to be monotonic. The mathematical construction has continuous first derivatives, while second derivatives can jump. This is the PCHIP family described in the [SciPy reference](https://docs.scipy.org/doc/scipy/reference/generated/scipy.interpolate.PchipInterpolator.html); the [reference implementation](https://github.com/scipy/scipy/blob/main/scipy/interpolate/_cubic.py) also documents the endpoint limiter. The product should describe its native interpolation and 8-bit lookup, not promise exact numerical derivative continuity, exact-real rounding, Photoshop parity or recovery of clipped detail.

## Numerical review

The prototype does not construct an overflowing `dy/dx`. It decomposes positive interval sizes and nonzero absolute output differences into a mantissa and exponent. Subnormals are first scaled by an exact power of two. Interior calculations form the smaller of a ratio and reciprocal, so exponent underflow produces a limiting zero rather than an infinity divided by infinity. Normalized interval weights remain finite and positive. The resulting tangent-to-secant factors stay in `[0,3]`.

Endpoint factors implement the one-sided formula `1 + f - f*(neighborSecant/currentSecant)` for equal signs and the corresponding addition for opposite signs, limited to `[0,3]`. The separated product can overflow to positive infinity, but this saturates the endpoint to its intended 0 or 3 limit. Zero factors/secants are handled before decomposition; there is no `0 * Infinity` or undefined secant. No finite minimum x spacing is needed for this implementation.

Each interval's two Bezier controls are built from these bounded factors and clamped to its endpoint output range. De Casteljau evaluation keeps finite intermediate values inside the convex hull; a final endpoint-range clamp is retained. In exact arithmetic, factors in the square `[0,3]²` give a monotonic cubic for an interval with nonzero secant: the derivative at the four corners of that factor square is a nonnegative quadratic, and it is affine in the factors. This supports per-interval shape preservation, including output reversals at knots. The finite implementation and byte quantization were separately checked rather than treating this mathematical argument as an exact binary64 guarantee.

The implementation should preserve these evaluation choices:

- Every authored knot whose x coordinate is an integer LUT input returns `Math.round(authoredY)` directly.
- Points all satisfying `x === y` produce the exact identity lookup, including adjacent/subnormal intervals.
- Two-point smooth curves use a mathematically straight line, with the same exact authored-knot rule.
- General smooth interpolation uses the declared native binary64 operation order and one final byte rounding. No hidden epsilon or exact-real half-tie claim is introduced.

There is an unavoidable distinction between exact smooth knots and legacy two-point bytes. For points `[(0,255), (255,0.49999999999999994)]`, the legacy expression rounds its final interpolation result to 0.5 and returns byte 1. The exact smooth endpoint returns byte 0. Four variants of this fixture are retained in the independent probe. Root explicitly chose exact smooth knots and unchanged legacy linear output, so a universal two-point byte-equivalence claim would be wrong.

## Independent experimental evidence

Run `node test-results/smooth-curves-review/probe.mjs`, then `python3 test-results/smooth-curves-review/exact_reference.py` from the repository root. These probes use only local generated inputs and the architect's test-only helper.

The current report covers **567 curves and 145,152 LUT bytes**: paired extreme x/y exponents, subnormal and adjacent input gaps, half-byte output neighborhoods, plateaus, reversals, decreasing curves, exact identity, the adversarial two-point endpoints and 100 seeded random curves. All finite-factor, endpoint-range, per-interval byte-monotonicity, integer-knot and identity checks pass. Four smooth endpoints differ from the old linear expression for the accepted reason above.

The independent Python reference uses exact fractions of the authored binary64 values, directly computes PCHIP derivatives and evaluates the Hermite power basis. It does not reuse secant decomposition, factor computation, Bezier controls or the proposed evaluator. It finds 520 byte differences from exact-real PCHIP across the expanded fixture set; each differs by one byte and lies within `1.42e-14` of the relevant mathematical half boundary. This includes deliberately adversarial two-point floating cases. The earlier 531-case set had only 12 differences, within `1.59e-22`; the expanded set intentionally adds many more half-boundary cases. These are declared floating semantics, not failures of interval bounds or a claim that arbitrary cases share a proven error bound.

The architect separately reports 30,042 additional curves, no finite/range/monotonic/knot failures, about 3 microseconds per 256-byte setup in its local measurements and photographic comparisons. Those owner results are not independent executions of this review's oracle.

## Compatibility and integration requirements

The old `normalizeParameters('curves', …)` accepts only `points` and `channel`, so a persisted nondefault `interpolation:'smooth'` fails closed in old native readers instead of silently rendering linear pixels. Do not introduce a permissive reader fallback. New readers must reject invalid interpolation strings, booleans, null and surplus parameter keys before image access. Canonical explicit linear omission preserves old sparse records and avoids needlessly making ordinary curves unreadable by an older companion. Existing accepted linear metadata must not gain unrelated validation restrictions.

Both global adjustments and source filters already delegate their parameter normalization and candidate lookup to `server/color.mjs`. Use a shared pure compiler for the new lookup rather than introducing a second algorithm for one path. Retain the existing linear expression literally; a cleaner-looking interpolation rearrangement can change half-boundary bytes.

Partial updates merge the current normalized parameters before changing interpolation: points/channel-only writes retain smooth, and interpolation-only writes retain points/channel. Explicit `'linear'` is the reset operation; omitting the field in a partial update is not a reset. `value` remains 0. A saved edit recipe stores the full canonical configuration through the same normalizer, preserves the smooth marker and omits linear. Validate recipes without compiling LUTs, reading assets, rendering or mutating the document. Recipe capability checks must cover both `add_layer_filter` and `update_adjustment` slots whose declared kind is curves, including disabled source entries, and invalidate a ready report on policy withdrawal. Import/replay must not discard interpolation.

Canonical recipe omission needs a specific execution rule: a complete Linear adjustment recipe applied to a currently Smooth target must reset the mode, not inherit it through the ordinary partial-update merge. The approved staging seam injects transient `interpolation:'linear'` only for normalized Curves adjustment recipe steps with an omitted mode. This argument is not stored in the recipe or its hash. Source recipe steps append new filters and therefore already receive the correct Linear default. Metadata-only validation and real application must stage the same reset.

Global and source alpha behavior deliberately differ today. Curves is not a member of `COLOR_MAPPING_KINDS`: the legacy global adjustment can transform hidden alpha-zero RGB while preserving alpha, except where protection or zero mask/opacity bypasses it. The source-filter evaluator skips alpha-zero RGB exactly. Smooth must retain each existing caller's policy. Adding Curves to `COLOR_MAPPING_KINDS` would also change old global yielding and alpha behavior and is outside this extension.

Source filters continue to combine source alpha before grading, round the curve candidate before entry blending/opacity, run the whole-stack effect mask after the finished stack, then perform geometry. Identity smooth curves remain structurally active and still participate in nonnormal blend modes and protection rules. Bake uses the same source evaluator, preserves source/alpha/geometry and follows existing guards/rollback. Global masks/protected pixels, isolated/clipped source restoration and generated exclusions stay in the existing callers. Native projects, portable bundles, undo and restart retain the new parameter. PSD support must retain its current adjustment/filter refusal or materialization behavior; this is not a new editable PSD curve exporter.

## Resources and UI acceptance

This remains one 256-byte lookup plus bounded setup for at most 15 intervals. The prototype's 8-byte decomposition view dies when segment setup returns; no full image plane, spatial cache, persistent table or per-pixel transcendental calculation is added. Production should return only the lookup or a scalar transform closure rather than retaining prototype diagnostics. Existing scalar filter work weight 1, blend surcharge and source/mask/Bake/Distort buffer phases remain appropriate. Do not call the compiler during metadata validation. The existing 256-byte Curves LUT was already part of the scalar path; this extension does not justify inventing a new image-sized reserve or relaxing any current admission.

The UI must draw the actual smooth lookup or shared evaluator instead of leaving a straight polyline that misrepresents the operation. It must retain exact saved fractions and invalid numeric strings until explicit submission. A concrete current-control issue needs correction within this UI slice: `movePoint` clamps x between neighboring coordinates plus/minus 1 even for Y-only edits. For saved x values `[0,0.1,0.2,255]`, changing the second point's y moves x from 0.1 to 1, crossing its neighbor. Numeric editing needs strict ordering without an integer-spacing clamp; pointer authoring can keep an explicitly bounded gesture policy without changing untouched saved coordinates. Smooth support and capability withdrawal must be handled separately from legacy linear support, on both global and source controls, without silently resetting the chosen interpolation or points.

The final capabilities are `curvesInterpolationPolicy:'shape-preserving-pchip-v1'` and `curvesInterpolationModes:['linear','smooth']`, used with the existing independent global/source kind and command gates. The environment-neutral helper is `shared/smooth-curves.mjs`, exporting `CURVES_INTERPOLATION_POLICY`, frozen `CURVES_INTERPOLATION_MODES` and `compileSmoothCurveLookup(points)` returning a fresh Uint8Array256. Missing new capability data leaves legacy Linear available through the omitted-field form; it cannot silently convert saved Smooth settings.

The completed [design](SMOOTH_CURVES_DESIGN.md) was cross-checked against these requirements and root approved implementation. No numerical or resource blocker remains after the accepted exact-knot/two-point clarification. Production acceptance will pin the adversarial endpoint, exact old linear output, extreme gaps, partial reset/merge, global versus source hidden RGB, blend/mask/Bake ordering, protected contexts, malformed portable/recipe preread rejection and real persistence/late transaction rollback.

## Maintained production audit

`node --test tests/smooth-curves-audit.test.mjs` passes **8/8**. The actual shared production compiler also matches all 567 prior prototype cases/145,152 bytes; `test-results/smooth-curves-review/production-report.json` records that comparison. Production source review confirms the bounded compiler's operation order, fresh-only lookup return, literal untouched Linear loop, separate Smooth dispatch, optional-mode normalization and transient recipe reset seam.

- The independent symmetric three-knot Hermite polynomial `4*x*(255-x)/255` and its reversed curve match all 256 bytes exactly, without using the runtime tangent/Bezier helper as an oracle. All four channels, adjacent/subnormal identity and finite interval cases pass. The adversarial endpoint pins Smooth 0 versus unchanged Linear 1, with all legacy Linear inputs checked through actual color dispatch.
- Sparse graph validation and partial source/global updates preserve unrelated points, channel, masks and density. Explicit Linear removes the canonical field. Pixel/model/asset spies and a temporary DataView-construction trap prove these metadata paths do not compile a Smooth lookup. Curves remains work weight 1, nonnormal blend 41, with no spatial cache or shared table.
- Three canonical recipe cases—omitted Linear, explicit Linear and Smooth—apply to existing Smooth adjustment targets and masked source stacks. Validation makes no filesystem calls or LUT setup, leaves the document unchanged and reports a stable hash. Application matches explicit equivalent commands, preserves mask scope, adds one undo step and does not rewrite the saved definition/hash. Undo restores the prior layers.
- Direct global adjustment fixtures confirm the established hidden-RGB grading behavior, exact alpha retention and the original mask-density/opacity/protection order. The same source settings skip hidden RGB exactly. Neither input buffer is mutated.
- Independent integer source-alpha combination, closed-form Curves candidate, rational Multiply/half opacity and native effective mask bytes match source pixels before an exact integer Distort. Actual Bake preserves the rendered appearance, raw working alpha, separate alpha, original source asset and retained geometry; the original files stay byte-identical.
- Actual lower protected content with soft alpha/outside outline, an isolated group and a generated clipping member retains its original protected appearance. Ordinary filtered source RGB restores at that footprint, generated isolated preview alpha is zero there, and source inspection remains unfiltered. Identity Smooth on a protected target and Bake over lower protected content reject before pixel access.
- Invalid interpolation values, surplus parameters and unordered points reject on native mutations and forged portable global/source/recipe graphs before filesystem/image/model access. The current document and asset files remain unchanged. Forging the manifest is intentional because the ordinary bundle encoder itself already rejects invalid recipe definitions.
- Real `ENOTDIR` persistence failure and a transaction that changes both modes, actually Bakes, paints, then fails on a missing layer leave the old modes, graph, history/project files and assets unchanged. Instrumentation verifies both pixel writes happened before the failure and their owned assets were removed.

The first audit run exposed three test-harness assumptions, not production defects: cleared stacks are empty arrays; lower-context Bake refusal has its specific `FILTER_BAKE_PROTECTED_CONTEXT` code; and malformed recipes cannot be exported by the normal encoder. The corrected maintained tests exercise the intended behaviors. No backend production blocker remains; UI source/browser review is separate and ongoing.

The source review covered `CurvesControl`, its parent drafts, individual source-filter and whole-stack ownership, and the narrow App result/preview/conflict paths. The owner corrected these findings before browser acceptance:

- Individual filter and global target/kind transitions now advance monotonic epochs, so selecting A, then B, then A cannot revive a pending result. - SVG pointer coordinates use the captured screen matrix and inverse. The same matrix must remain current at move/up; inverse linear deltas preserve no-motion axes and the original grab offset. This corrects the border-versus-viewBox mismatch found by root.
- A Curves row checkbox captures the row's actual kind even when a different filter is selected. It therefore receives the same guarded preview and stale-refresh path as Curves Apply.

Pointer cancellation restores exact pre-drag strings only within the same draft session; foreign pointers cannot finish the ticket. The existing shared compiler draws the actual 256-byte Smooth lookup. The App checks the captured context before accepting metadata and again before publishing an awaited preview; a conflict refresh is owned and never replays the edit.
