# Next professional color workflow: independent comparison

Status: **read-only research and design probes, 2026-09-19; no next-feature production changes or implementation approval**. Selective Color is closed with root's1016 integrated checks and the owner's67 browser workflows/build. Architecture owns the more detailed targeted-HSL evaluation. This document compares the three candidates against the actual current renderer and persistence paths.

## Recommendation

Prioritize **a distinct targeted Hue/Saturation/Lightness adjustment** if its dark/pastel targeting and numerical tests pass. It adds direct color-family editing that existing scalar Hue, scalar Saturation and Selective Color do not provide. **Independent master/R/G/B Curves banks** are the lower-risk second choice: most of their pixel behavior already exists, and they consolidate a useful four-entry workflow into one editable adjustment. **Imported 3D `.cube` looks** have strong interchange value but should follow a typed non-image asset design; treating a file reference as ordinary adjustment metadata would leave portability, recipes and resource ownership incomplete.

| Candidate | Concrete workflow improvement | Current approximation | Main new risk |
| --- | --- | --- | --- |
| Targeted HSL | Shift foliage hue or reduce a color family's saturation while retaining other families in one adjustment | Whole-image scalar controls, selections/masks or indirect Selective Color edits | Range influence, hue wrapping and exact candidate rounding |
| Four Curves banks | Keep tone contrast and separate channel corrections under one mask/opacity and one saved configuration | Four ordered Curves entries | Composition order, nested partial updates and retained precise drafts |
| 3D `.cube` import | Reuse a look from another grading application | Rebuild the look with native controls/recipes | Typed assets, color-space assumptions, bounded table preparation and transferable recipes |

This is not a request to add another general color matrix or Gradient Map. `server/color.mjs` already registers Channel Mixer, Gradient Map, Color Balance, Black & White, Smooth Curves and Selective Color: 25 global kinds and 29 source kinds at review time. Older inventory prose still lists some completed controls as missing, so it is unsuitable as the sole prioritization source.

## Targeted HSL: highest additional control value

Adobe's current Hue/Saturation documentation describes Hue, Saturation and Lightness controls, selection of prominent colors and adjustable range/falloff handles. That supports a targeted-color workflow, but does not specify the complete pixel algorithm. A fixed six-range native implementation would be a narrower feature than those automatic detection and adjustable-range tools. [Adobe Hue/Saturation documentation](https://helpx.adobe.com/photoshop/desktop/adjust-color/color-corrections/apply-a-hue-or-saturation-adjustment.html)

The smallest complete candidate is a new parameterized global/source kind, zero defaults, one Master row plus six retained color-family H/S/L rows, original-input memberships and one final candidate byte result. It should leave the old scalar `hue`, `saturation` and `vibrance` algorithms literally unchanged: current Hue uses its existing chroma rotation, while Saturation scales distance from encoded Rec.709 luma. Neither is interchangeable with a new HSL-space operation.

Required decisions before implementation are the membership policy, saturation/lightness formulas, admitted precision and final rounding contract. Master and targeted controls should combine from the same input classification, with a declared aggregate clamp and wrap. Applying each color row sequentially would produce row-order dependence and reclassification. Gray must not acquire an arbitrary hue through numerical noise. Exact default identity, hue wrap at Reds, equal-channel ties, full desaturation and dark/pastel cases need direct fixtures.

The first architecture candidate used adjacent chromatic cube weights divided by 255. Its six weights sum to input chroma/255. This is bounded and avoids hue division, but its influence fades near black and white as well as near gray: `[32,0,0]` and `[255,223,223]` have fully saturated HSL hue yet only 32/255 total influence. Reds Saturation −100 would therefore not fully desaturate them. This is a product-semantic choice, not just a rounding issue. I asked architecture to compare those fixtures and photographs against hue-normalized memberships or an explicitly stated chroma fade before freezing the contract.

The subsequent comparison selected hue-normalized Hue/Saturation, chroma-attenuated named Lightness and proportional saturation. This preserves dark/pastel desaturation while suppressing large named-Lightness jumps and positive-saturation grain near gray. The completed independent [targeted-HSL review](TARGETED_HSL_REVIEW.md) finds no remaining design blocker for that explicit contract; this comparison's earlier alternatives remain useful provenance rather than competing implementation requests.

The renderer fit is otherwise strong: bounded compiled controls, no external asset or neighborhood plane, ordinary source blend/opacity and whole-stack mask order, existing Bake and original-source retention. The actual computing work weight must follow worst-case arithmetic measurements, including all-channel exact-round fallback if one is needed. Global/source capability markers must independently gate the new kind, full rows must survive partial updates and recipe capture, and old readers should reject the unknown kind. New global hidden-RGB behavior must be pinned explicitly, rather than changing older scalar policies.

## Curves banks: smallest implementation risk

Adobe documents selecting individual color channels within Curves and displaying component curves over the composite curve. That supports keeping multiple channel settings together, without establishing a native composition order or numerical equivalence. [Adobe Curves documentation](https://helpx.adobe.com/photoshop/using/curves-adjustment.html)

The current native parameters contain **one** point set, one channel selector and optional Smooth interpolation. Switching the channel changes where that same curve acts; it does not retain four separate curves. Four existing full-opacity Normal source entries can already express Master followed by Red, Green and Blue, but consume half of the eight-entry layer limit. Their separate blend/opacity stages also differ from one banked correction with one final blend/opacity.

A complete bounded extension would retain four independently authored point/interpolation records, default missing banks to identity, and expose a bank selector with per-bank and all-bank resets. Keep every bank's exact string draft and hidden validation state. Bank switching must be local inspection, not a replacement of another bank's points. Existing precise point selection, subnormal/adjacent spacing, captured SVG coordinates, keyboard editing and cancellation ownership remain necessary.

Prefer an explicit mutually exclusive banked representation under Curves, rejected by old strict parameter readers, while retaining the old `{points, channel, interpolation}` path unchanged. Do not silently reinterpret saved single-curve records or migrate them during ordinary reads. A deliberate UI upgrade can place an old RGB curve into Master or an old component curve into the corresponding bank. Supplied bank records should replace that complete bank; omitted banks retain on partial update. Recipes should capture all four effective banks and their interpolation so applying a default recipe resets an existing nondefault target. Never mix an ambiguous legacy point set with bank metadata.

Pin an order such as **Master byte LUT, then corresponding component byte LUT**, with byte quantization at both stages, before the entry's single blend/opacity. This directly represents a declared sequence of current curves. Reversing the order or delaying the first byte round changes pixels. The independent probe `test-results/next-pro-workflow-review/curves-banks-probe.mjs` composes actual current Linear/Smooth transforms for 32 bank configurations and compares **24,576 bytes** against four sequential transforms. Every byte matches. It also records an order counterexample (`[1,150,66]` gives `[1,182,99]` versus `[2,182,99]`) and a two-stage rounding counterexample (two half-scale stages map byte 1 to 1, while only rounding at the end gives 0).

Three composed 256-byte output tables require **768 retained table bytes** and only three channel lookups per pixel. A straightforward sequential composition can bound its table peak at five 256-byte tables: Master, two finished outputs, a raw third channel and its composed output. Existing Smooth compiler setup and bounded point/coefficient objects are additional, separately scoped allocations. No extra image surface is needed. Benchmark compilation and the actual hot loop before deciding work weight; four bank controls do not require four image passes. Preserve current global Curves hidden-RGB behavior and the source path's alpha-zero skip. Identity banks remain structurally active under nonnormal filter blending.

## 3D `.cube`: useful, but needs complete asset ownership

Adobe exports CUBE alongside other color-table formats for use in Photoshop and other image/video applications. Grid size trades file size against approximation quality; exporting a look does not make its assumed input color space self-describing. [Adobe LUT export documentation](https://helpx.adobe.com/photoshop/using/export-color-lookup-tables.html)

The maintained OpenColorIO Iridas Cube reader documents RGB triplets with the red coordinate varying fastest, optional domains, separate 1D or 3D data, and outputs that may extend below 0 or above 1. Its implementation is a useful primary format reference, not a reason to accept every variant in an RGB8 first slice. [OpenColorIO Iridas Cube reader](https://github.com/AcademySoftwareFoundation/OpenColorIO/blob/main/src/OpenColorIO/fileformats/FileFormatIridasCube.cpp)

OpenColorIO's tooling separately specifies the color space expected by a look when wrapping it for ACES, illustrating why a `.cube` filename alone cannot establish the required input transform. Prism should not infer log, scene-linear or HDR semantics from a title. [OpenColorIO usage documentation](https://opencolorio.readthedocs.io/en/stable/guides/using_ocio/using_ocio.html)

A possible bounded first slice is a **3D-only, size 2–33, RGB [0,1] table applied to encoded sRGB**, accepting only absent or identity domain, with no 1D shaper, combined pipeline or extended-range samples. Unsupported domain/data must reject before publication, rather than silently clipping the imported table into a different look. Pin table ordering, interpolation (trilinear or tetrahedral), parsed sample precision, endpoint handling and final byte round. Test all 256 input levels on each identity axis, asymmetric tables that catch transposition, cube boundaries and half ties. This limited format must be described as such; it will not load every professional `.cube` file.

The current seams make this more than a transform helper:

- `server/project-bundle.mjs` enumerates raster `asset`, `sourceAsset`, `alphaAsset` plus the preserved source-document asset. `server/native.mjs::projectAssetUses` and `validateProjectAsset` then apply matching image/PSD validation. A LUT referenced only inside filter/adjustment parameters would not be carried or validated by that asset walk.
- `adjustmentTransform` compiles synchronously. LUT bytes need bounded verified preparation before the RGB loop, with no filesystem reads from the per-pixel function and metadata-only admission before image reads.
- A 33³ RGB table holds 107,811 numbers: 431,244 bytes as Float32 or 862,488 as Float64. Parse buffers, text, canonical bytes and compiled table lifetimes must be counted. A shared cache needs a global retained bound across distinct assets/leaves; it cannot be hidden inside a per-leaf maximum or omitted from Bake and Distort phases.
- Recipes are currently self-contained metadata with a 32 KiB per-recipe and 256 KiB library limit. A normal 33³ table cannot be embedded there unchanged. A bare local hash would break transfer to another project. Complete LUT recipe support needs a typed dependency/package extension, or an explicit capture/application refusal until that extension exists.
- Import must atomically publish an immutable content-addressed asset and graph reference, preserve original bytes/provenance when promised, verify dedupe contents through the bounded reader, and clean owned files after actual save or late-transaction failure. Undo/history references, `.prism` export/import and restart must retain the LUT; ordinary Clear/Bake must not accidentally remove assets still used by history or another layer.

These are concrete prerequisites, not reasons to weaken existing image validation. The smallest complete user flow includes bounded file import, a readable look name/size/input assumption, source/global application, explicit opacity, undo, restart, project transfer and truthful recipe support. No preset pack or broad OpenColorIO dependency is needed. If reference source is copied, preserve its applicable license notices; the reviewed OpenColorIO license contains source/binary redistribution conditions. [OpenColorIO license](https://github.com/AcademySoftwareFoundation/OpenColorIO/blob/main/LICENSE)

## Decision gate

Targeted HSL should advance only after the independent range-utility review and actual arithmetic/fallback benchmark. Curves banks can proceed through a small separate compatibility/UI design if HSL's semantics remain unsettled. LUT import should wait for an agreed typed asset and recipe dependency contract. All three must retain existing source alpha, protected/generated composition, filter-stack mask placement, resource preflight and atomic publication guarantees; none requires changing legacy scalar pixels or claiming Photoshop numerical parity.
