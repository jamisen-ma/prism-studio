The proposed linked-corner authoring mode is a useful bounded addition to existing Distort. It can make a pair of corner edits with one gesture while persisting the same four numeric corners. It needs no new transform type, sampler, resource limit, native command or portable asset. Existing source-filter ordering, document-space masks, fixed output clipping and native protection remain authoritative.

Adobe's current transform overview distinguishes freely moved Distort corners from symmetric linked corner movement for Perspective. ## Numerical rule and preservation requirements

Use the existing corner order TL, TR, BR, BL. Horizontal linking changes X only, with partner indices `[1,0,3,2]`; vertical linking changes Y only, with partner indices `[3,2,1,0]`. These are stage/document axes, not the direction of an already rotated or skewed edge.

For selected coordinate `a`, partner coordinate `b` and a single captured-axis delta `d`, compute `a + d` and `b - d` from the original captured values. Preserve all six untouched coordinate strings. Do not reconstruct the partner from a rounded midpoint, derive a new rectangle, symmetrize an arbitrary saved quad, or accumulate deltas from preceding pointer events. This lets repeated events and a direct final event produce the same corners.

The operations are binary64 additions/subtractions. The mathematical pair midpoint is constant, but the implementation must not promise exact floating-point midpoint equality or exact reversibility after separate gestures. For example, adding `1e-12` to `16384` can round back to the same coordinate while subtracting it from a zero partner changes that partner. Tests should pin the declared operations and untouched values, rather than hide this with an epsilon or snap. A zero captured-axis delta must return the exact baseline strings, including scientific notation and signed-zero spelling, without reformatting. The pure helper likewise preserves every untouched Number and a zero-delta owned copy, including signed zero; only changed coordinates evaluate the declared operations. The existing native normalizer owns later serialized zero canonicalization. Movement on the ignored axis must have the same no-change behavior.

Apply the same delta to both members even near a boundary. Independent clamping would silently change the rule. Finite off-limit corners may stay as an invalid draft; they must not be submitted until corrected. Crossing, thin, singular or pole-adjacent quads may also be authored temporarily, with the existing native validator refusing them on Apply. Keep its `maxCorner`, convexity, conditioning, denominator and work/memory limits. Do not add a client approximation of native homography admission.

For any new numeric delta field, parse the whole finite decimal/scientific string and reject lexical nonzero underflow instead of silently treating it as zero. Preserve an exact zero action as a no-op. Root and both owners agreed to retain all eight independent corner fields and add a separate selected-corner/delta **Move pair** action. That action and pointer dragging use the same delta-only helper; no absolute-coordinate overload is needed. A completed nonzero local action resets its delta text to zero to prevent an accidental repeated move.

Independently evaluated binary64 discriminators for the selected/partner coordinates are:

| `s`, `p`, `d` | `s+d`, `p-d` | Required consequence |
| --- | --- | --- |
| `16384`, `0`, `1e-12` | `16384`, `-1e-12` | Do not recover delta from the rounded selected result. |
| `1`, `1`, `Number.MIN_VALUE` | `1`, `1` | A representable nonzero delta can leave both coordinates unchanged. |
| `Number.MIN_VALUE`, `1`, `Number.MIN_VALUE` | `1e-323`, `1` | Preserve a change that survives on only one member. |
| `0.1`, `0.3`, `0.2` | `0.30000000000000004`, `0.09999999999999998` | Do not decimal-snap or reassociate the declared operations. |
| `0`, `16384`, `-32768` | `-32768`, `49152` | A bounded candidate may exceed the native authoring range on both members. |

For a helper limit `L`, bounding baseline coordinates to `±L` and finite delta to `±2L` gives finite output coordinates within `±3L`; `L≤16384` makes the proof trivial without a runtime epsilon. A separate `withinBounds` result checks the actual native `±L` boundary. The final design chooses complete cancellation for a nonfinite or over-helper-bound pointer delta: restore captured strings, release capture, invalidate the drag and show a notice. A helper-bounded but native-out-of-range result installs both computed coordinates in the local draft, resets the action delta and disables Apply until correction. Its numeric fields persist after pointer release; the existing invalid guide may disappear. This distinction prevents silent clamping and prevents stale bounded coordinates from appearing to represent the user's final gesture.

## Existing source and ownership boundaries

[`distort-model.ts`](../client/distort-model.ts) already owns exact corner drafts, capability signatures, stage frames and result matching. [`Distort.tsx`](../client/Distort.tsx) already captures the original pointer position, draft, stage frame and displayed rectangle; Apply acknowledges the exact saved transform transition before metadata publication. Extend this controller rather than adding a separate competing inspector or local image warp.

The gesture must capture its link mode, selected corner, partner, baseline strings/numbers, pointer ID, stage/revision, session epoch, capability signature and displayed coordinate mapping. Check live ownership at both move and pointer-up. A mode/target/stage/tool/view/capability change, Escape, pointer cancellation, lost capture or component teardown must cancel and restore the original draft when the original editor still owns it. A foreign pointer must neither move the corners nor end the active capture. Busy state must stop a new gesture and cancel an active one before it can alter a draft or send a command.

Changing a local mode alone must not mutate corners or create history. The final rule disables/refuses mode and pair changes during a drag or command; a later mode never reinterprets a captured drag. A nonzero/incomplete/invalid pending numeric delta blocks Apply and mode/corner/stage switching until Move pair or Clear delta. Existing independent fields may correct the baseline before the deliberate local action. Keep the existing read-only retained-stage navigation during a pending command when no delta is unresolved; it invalidates the old submission. Close remains explicit whole-editor discard, including a pending delta. Do not weaken response/preview ownership to support any selector.

Canvas handles remain limited to a new or trailing Distort stage. Historical stage coordinates belong to that stage's frame and cannot be drawn over later transforms without another mapping. Numeric paired editing of historical stages is feasible, but must continue to submit their full `transformIndex`, captured revision and original frame. It must not silently append a replacement stage.

The current handle mapping uses captured displayed-rectangle dimensions and frame dimensions, so the delta rule should use the same declared coordinate system at every zoom. Preserve the existing off-center grab delta. If a chosen screen mapping changes at pointer-up, restore the baseline instead of committing the last event against a new scale. Guides describe the draft only; native pixels still update on Apply.

## Bounded acceptance proposal

- Pure authoring fixtures cover all four selected corners in both axes; rectangular and asymmetric/rotated baselines; positive/negative/zero deltas; ignored-axis motion; exact untouched strings; repeated-event independence; representable tiny/large coordinates; partner overflow and invalid intermediate geometry without clamping.
- The actual client helper should be imported through the current Vite loader, not copied or reimplemented inside its audit. Keep a small independently authored rule/reference for expected paired coordinates.
- Browser checks cover off-center grabs at two zooms, all four pair choices, keyboard access to any paired numeric action, foreign pointers, Escape/lost capture, mode switching, view changes at pointer-up, busy/capability away-back and target/stage navigation. A held command/preview must retain the existing owned-result rules.
- One native-equivalence fixture submits the authored corners through existing add/update commands and compares them with directly entered identical corners, including original asset retention and portable reopen. Existing Distort pixel/resource tests remain the sampler evidence; this client feature needs no new full renderer benchmark.

There is no native compatibility blocker: older Distort-capable readers already understand the resulting record. The final contract is session-local Free/Horizontal/Vertical modes, an explicit selected-corner/delta Move pair action, unchanged independent corner fields, disabled mode switches during capture or pending submission, and the bounded recovery/ownership rules above. The owner design now pins these decisions. The UI owner aligned pending-command stage inspection and explicit Close wording with the existing controller. Independent conceptual signoff is clear.

Initial controller review found two concrete issues, also independently confirmed by root. Accepted Remove copied an unapplied invalid/nonzero delta into the newly selected stage despite explicitly discarding the old draft. Clear delta was both visually and handler-gated by full editability, preventing its intended local escape after capability loss, protection or a stale revision. The owner corrected both: only an owned accepted Remove resets movement to Free, selected corner to TL and delta to zero, while ordinary Apply retains its mode/corner and refusal retains the draft. A separate idle, non-drag Clear action changes only delta and is available independently of editability; every corner string stays intact. The matching button uses the same busy/capture restriction. Both fixes were source-reviewed, and the owner added focused remove-with-`1e` and policy-withdrawn Clear cases. No shared-helper, renderer or command change was required.

The final controller source captures mode, target/capability/revision, geometry and original strings before dragging, checks the live owner at move/up, cancels on busy/ownership/geometry changes, and ignores foreign pointers. Linked samples always start from the captured baseline; over-helper-range movement cancels rather than leaving a stale candidate. Pending numeric actions cannot be silently applied or discarded by stage/mode selection. Existing result acknowledgement and preview ownership remain in the existing Distort runner, with no App retry or renderer change. Independent source signoff is clear.
